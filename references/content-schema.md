# Схема content.json

Единственный источник данных для рендера. Claude заполняет этот JSON из свободного
описания пользователя и передаёт файл в `scripts/generate.js`. Не добавляй полей
сверх схемы — неизвестные поля игнорируются рендером.

Если данных для поля нет и оно не помечено ниже как «опционально» — не выдумывай
значение. Поставь строку `"TBD"` (для строк) и обязательно предупреди пользователя
в чате, какие разделы нужно дополнить. Числовые обязательные поля (например, цены)
без данных лучше вообще не включать в `items`/`total` и явно спросить пользователя,
чем проставлять 0 или выдуманную цифру.

## Верхний уровень

| Поле | Тип | Обязательно |
|---|---|---|
| `meta` | object | да |
| `cover` | object | да |
| `problem` | object | да |
| `solution` | object | да |
| `scope` | object | да |
| `timeline` | object | опционально |
| `pricing` | object | да |
| `cases` | object | опционально |
| `terms` | object | опционально — слайд рендерится всегда, `paymentTerms` подставляется автоматически |
| `contacts` | object | опционально — слайд рендерится всегда, `personName`/`messenger` подставляются автоматически |
| `outputSlug` | string | да — короткий латинский slug для имени папки вывода, например `"romashka-delivery-app"` |

## `meta`
```
{
  "clientName": "ООО «Ромашка»",
  "projectTitle": "Мобильное приложение доставки",
  "date": "2026-08-02",           // ISO-дата, если не указана — сегодняшняя
  "proposalNumber": "KP-2026-014", // опционально, можно "TBD"
  "preparedBy": "Агентство «Вектор»"
}
```

## `cover`
```
{
  "title": "Заголовок обложки — обычно = projectTitle или ярче",
  "subtitle": "Одна фраза о ценности предложения для клиента"
}
```

## `problem` и `solution`
Одинаковая форма для обоих:
```
{
  "heading": "Задача" | "Решение",
  "body": "1-2 абзаца свободного текста",
  "points": ["короткий тезис 1", "короткий тезис 2"]  // опционально, 2-5 штук
}
```

## `scope`
```
{
  "heading": "Этапы работ",
  "stages": [
    { "title": "Этап 1. Аналитика и дизайн", "description": "...", "result": "Кликабельный прототип" },
    { "title": "Этап 2. Разработка", "description": "...", "result": "Рабочее приложение" }
  ]
}
```
Минимум 1 этап. Обычно 3-6. Если проект по своей природе делится на MVP и
расширенную (FULL) версию — отрази это прямо в `stages`, группируя этапы под
явными заголовками, например `"Этап 2. MVP: веб-платформа и админка"` и
`"Этап 5. FULL: расширение каналов"` (см. `kp-writing-guide.md`, раздел про
MVP/FULL). Отдельного поля для этого в схеме нет — используются обычные
`stages` с говорящими названиями.

Длинные списки `stages` автоматически распределяются по нескольким слайдам
(`scripts/render-html.js`, `chunkStages`) — не сокращай контент искусственно
из опасения, что он не поместится.

## `timeline` (опционально, но желательно)
```
{
  "heading": "Сроки",
  "totalDuration": "8 недель",
  "milestones": [
    { "label": "Этап 1. Аналитика и дизайн", "duration": "2 недели" },
    { "label": "Этап 2. Разработка", "duration": "4 недели" }
  ]
}
```

## `pricing`
```
{
  "heading": "Стоимость",
  "currency": "₽",
  "items": [
    { "title": "UX/UI-дизайн", "description": "...", "price": 150000 },
    { "title": "Разработка", "description": "...", "price": 550000 }
  ],
  "total": 700000,
  "packages": [   // опционально, если предложены тарифы вместо одной сметы
    { "name": "Базовый", "price": 500000, "includes": ["...", "..."] },
    { "name": "Расширенный", "price": 850000, "includes": ["...", "..."] }
  ]
}
```
Либо `items` + `total`, либо `packages` — можно и то, и другое. Если стоимость не
известна, оставь `items: []`, `total: "TBD"` и обязательно спроси пользователя.

## `cases` (опционально)
```
{
  "heading": "Наши кейсы",
  "items": [
    { "title": "Название проекта", "description": "...", "result": "Метрика/результат" }
  ]
}
```
Если пользователь не упоминал портфолио — просто не включай `cases` в JSON, слайд
пропустится автоматически.

## `terms` (опционально в content.json)
```
{
  "heading": "Условия",
  "validUntil": "2026-09-01",
  "notes": "Любые доп. условия одной строкой"
}
```
`paymentTerms` обычно **не указывать** — `scripts/render-html.js` подставляет
его из `assets/agency-defaults.json` (агентская политика по умолчанию:
поэтапная оплата — предоплата за этап → работа → приёмка → предоплата
следующего этапа). Указывай `paymentTerms` явно только если для конкретной
сделки пользователь прямо сказал, что условия другие (например, полная
оплата авансом за небольшой проект) — тогда значение из content.json
используется вместо дефолта. Слайд с условиями рендерится всегда, даже если
весь блок `terms` опущен.

## `contacts`
```
{
  "heading": "Контакты",
  "role": "Руководитель проектов",     // опционально
  "cta": "Готовы начать на этой неделе — напишите нам"
}
```
`personName` и `messenger` обычно **не указывать** — подставляются из
`assets/agency-defaults.json` (сейчас: Марат Магсумов, `@educ_founder`).
Указывай их явно только если пользователь для конкретного КП прямо назвал
другого контактного человека. `phone`/`email` можно добавить, если для
конкретного КП это уместно — шаблон их отрендерит, но по умолчанию агентство
их не использует.

## Правила для Claude при сборке JSON

1. Разделы, отмеченные «опционально» и не упомянутые пользователем — не включать
   в JSON вовсе (не заполнять пустышками).
2. `scope.stages` и `pricing` — минимальный набор, без которого КП не имеет смысла;
   если их нечем заполнить, сначала спроси пользователя, не запускай рендер.
3. `contacts.personName`/`messenger` и `terms.paymentTerms` в content.json обычно
   не указывать — по умолчанию берутся фиксированные значения агентства
   (`assets/agency-defaults.json`). Указывай их явно только когда пользователь
   прямо задал другие условия/контакт именно для этой сделки — тогда значение
   из content.json имеет приоритет над дефолтом.
4. Формат вывода всегда `pdf,png` — не спрашивай пользователя, какой формат нужен.
5. Три поля — **клиент/компания**, **что входит в MVP/первую версию**, **что
   входит в FULL/расширенную версию** — заполняй из материалов проекта (ТЗ,
   описание, вложения, переписка), а не переспрашивай по умолчанию. Спрашивай
   пользователя только если этой информации действительно нигде нет.
6. Перед сборкой `pricing`/`timeline` изучи полное ТЗ и материалы проекта и
   предложи пользователю минимальную конкурентную цену и сроки (проект
   реализуется вайб-кодингом силами команды разработчиков — это быстрее и
   дешевле классической разработки, используй это для конкурентной цены).
   Дождись подтверждения цифр от пользователя и только затем собирай JSON —
   подробный алгоритм в `SKILL.md`.
7. Тон текста — деловой, без канцелярита и без чрезмерного маркетингового пафоса
   (подробнее — `kp-writing-guide.md`).
8. Перед запуском `scripts/generate.js` файл `content.json` должен пройти
   `scripts/validate-content.js` (вызывается автоматически внутри `generate.js`).
